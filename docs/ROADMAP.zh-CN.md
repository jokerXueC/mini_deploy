# mini_deploy 开源开发计划

本文档用于规划 mini_deploy 后续功能、工程建设和开源发布节奏。它不是承诺固定日期的排期，而是按风险和依赖关系排列的实施顺序。

## 1. 项目目标

mini_deploy 面向个人开发者、小团队和低配置 Linux 服务器，提供一套轻量、可自托管的部署面板。

长期坚持以下原则：

- 服务器端优先支持 Linux、systemd、Nginx 和 Docker Compose。
- 运行时尽量只依赖 Python 标准库，不引入数据库和重型服务。
- 部署动作必须可审计、可取消、可回滚，失败时给出可执行的排查信息。
- 默认配置优先保证安全，危险兼容选项必须显式开启。
- 安装、升级和卸载不得删除业务代码、数据库数据、Docker Volume 或用户配置。
- UI 保持轻量，核心操作不依赖前端构建工具也能运行。

## 2. 当前能力基线

当前版本已经具备：

- Gitee、GitHub、GitLab Push WebHook 接入。
- 多项目配置和每项目独立 WebHook Token。
- 串行部署队列、手动部署、取消、超时和回滚。
- 项目初始化、部署脚本模板、systemd 初版服务和 Nginx 配置生成。
- 部署前体检、部署锁检查和异常解锁。
- 部署历史、阶段耗时、变更文件和日志下载。
- CPU、内存、磁盘、网络及 Docker 容器监控。
- 企业微信、钉钉和邮件通知。
- 管理员登录、Session、CSRF 校验和审计日志。
- 安装脚本、服务器诊断脚本和基础中文文档。
- 固定公网入口 `http://服务器公网IP:6868`，无需域名即可登录；域名 HTTPS 作为可选入口。
- 业务项目上传证书的网页管理：有效期、替换、改名、HTTPS 启停和安全删除；不接管外部站点或自动续签。
- Nginx 接入引导：检测并选择本机/Docker 实例，校验目录挂载和网络，保存项目后端并检查连通；容器内配置检查、重载和证书路径转换已接入。暂不自动重建现有容器，Linux/Docker 实机验收仍需完成。

后续工作重点不是继续堆功能，而是先补齐安全、测试、升级和发布能力。

## 3. 版本路线

| 阶段 | 目标 | 主要内容 | 发布条件 |
| --- | --- | --- | --- |
| `v0.1.0` | 首个公开测试版 | 安全加固、升级保护、测试和开源文档 | 不存在已知高危问题，核心流程有自动化测试 |
| `v0.2.0` | 部署可靠性版 | WebHook 幂等、队列恢复、高级灾备和统一的本机运维 CLI | 重启后状态可恢复，重复请求不会重复部署 |
| `v0.3.0` | 使用体验版 | 首次接入向导、事件中心、配置校验和 UI 完善 | 新用户可仅按 UI 引导完成首个项目接入 |
| `v0.4.0` | 扩展能力版 | 平台适配器、通知扩展、模板包和公开 API | 扩展新平台时无需修改核心部署流程 |
| `v1.0.0` | 稳定版 | 稳定配置格式、升级兼容承诺和完整文档 | 至少经过两个小版本公开验证，无阻塞级缺陷 |

CLI 按以下边界分期，避免把本机运维命令、远程 API 和扩展生态混为一项：

- `v0.1.0`：保留现有 `agent.py admin ...`，并提供完成备份、最小恢复、版本回滚和安全卸载闭环所需的服务器终端入口；不要求统一成完整 CLI。
- `v0.2.0`：把状态、项目、部署、配置、灾备和管理员操作统一到仅供服务器本机使用的 `mini-deployctl`，不依赖公开 API Token。
- `v0.4.0` / P3：在本机 CLI 已稳定的基础上增加版本化公开 API 和可选远程客户端模式，并引入独立、可授权和可撤销的 API Token。

### 4.1 WebHook 密钥安全

要做什么：

- 默认禁止通过 `?token=` 和 `?secret=` 传递 WebHook Token。
- 保留 Gitee、GitLab Token 请求头和 GitHub HMAC-SHA256 签名。
- HTTP 日志统一隐藏 `token`、`secret`、`signature` 等敏感参数。
- 文档和 UI 生成的接入说明全部使用请求头或平台原生 Secret 配置。

怎么做：

1. 增加 `DEPLOY_ALLOW_QUERY_TOKEN=false`，默认关闭 URL Token 兼容。
2. 把签名校验拆成平台无关的验证函数，并为不同请求头编写测试用例。
3. 在 HTTP 访问日志写入前解析 URL，只记录路径和脱敏后的参数名。
4. 对旧配置给出一次迁移警告，不在日志中输出实际 Token。

验收标准：

- 默认配置下，URL Token 请求返回 `403`。
- 请求头 Token 和正确的 HMAC 签名可以正常触发部署。
- Agent、Nginx 示例日志和审计日志中均不出现明文 Token。

### 4.2 管理员首次初始化

要做什么：

- 消除公网首次访问者抢先设置管理员密码的风险。
- 提供服务器终端设置、重置管理员密码的标准命令。

怎么做：

1. 安装阶段在终端交互生成管理员密码哈希和 Session Secret。
2. 先提供稳定的 `agent.py admin set-password` 和 `admin reset-session` 终端入口；`v0.2.0` 再由仅供服务器本机使用的 `mini-deployctl` 统一封装。
3. 如果环境中没有密码，Web 页面只显示初始化被锁定，不直接接受公网设置。
4. 如保留网页初始化，则必须使用一次性随机初始化 Token，并限制有效期和尝试次数。

验收标准：

- 新服务器安装完成时已经存在管理员凭据。
- 未初始化状态不能通过公网直接创建管理员。
- 重置密码后旧 Session 全部失效。

### 4.3 权限与 systemd 加固

要做什么：

- 降低面板进程以 root 身份运行带来的整机风险。
- 明确 Agent、部署脚本和系统配置之间的权限边界。

怎么做：

1. 创建专用的 `mini-deploy` 系统用户运行 HTTP、状态采集和配置读取。
2. 将需要 root 的操作放入单独的受限执行器，仅允许预定义动作。
3. 执行器通过 Unix Socket 通信，校验项目标识和参数，不接受任意 Shell 文本。
4. systemd 增加 `ProtectSystem`、`ProtectHome`、`PrivateDevices`、`ReadWritePaths`、`RestrictAddressFamilies` 等限制。
5. 在权限拆分完成前，在文档中明确当前 root 模式的威胁模型和部署要求。

验收标准：

- Web Agent 本身不以 root 运行。
- UI 请求无法构造任意命令或任意文件路径。
- 受限执行器只允许操作配置中已经登记的项目。

### 4.4 安全升级、备份和卸载

当前已落地的是升级前 `format=2` bundle、只读 `scripts/verify_backup.py` 和跨 Agent/安装/备份的维护锁。安装器会在修改现有安装前自动校验刚创建的 bundle；校验器不解压、不恢复，也不代表恢复命令已经实现。活动 `projects.json` 默认位于 `/var/lib/mini-deploy-agent`，旧默认路径只会在备份成功后迁移；首次迁移的内容冲突或未纳入归档的自定义路径会安全终止，环境文件已选择数据目录后则以该副本为唯一权威配置。排队成功的部署/项目回滚任务会持有共享锁，维护中的新触发返回 HTTP `503`，配置、状态和审计写入等待。systemd 在服务重启时保留 `/run/mini-deploy-agent`，并在服务器重启后重建这个临时运行目录。下列版本目录、恢复、版本回滚和卸载工作仍是计划，不是当前能力。

要做什么：

- 升级时不删除配置备份、用户日志和状态数据。
- 支持失败后快速回到上一个版本。

怎么做：

1. 将持久数据统一迁移到 `/var/lib/mini-deploy-agent`，日志放在 `/var/log/mini_deploy`。
2. 程序文件采用 `/opt/mini_deploy/releases/<version>` 目录和 `current` 软链接。
3. 升级时先校验新版本，再原子切换软链接并重启服务。
4. 保留最近三个程序版本和指定数量的配置备份。
5. 增加 `upgrade`、`rollback-version`、`backup`、`restore` 和 `uninstall` 命令。
6. 卸载默认保留项目代码、配置、日志和备份，删除数据必须二次确认。

`v0.1.0` 的 P0 只要求服务器终端可完成安装版本备份、最小恢复/版本回滚和安全卸载闭环，不要求这些入口已经统一成 `mini-deployctl`。加密导出、诊断包、UI 备份列表和统一的本机运维 CLI 放在 `v0.2.0` 继续完善；公开 API 和远程客户端模式属于 `v0.4.0` / P3。

验收标准：

- 从旧版本升级失败时，服务自动恢复到旧版本。
- `.backups`、`projects.json`、环境文件和状态文件不会被覆盖或删除。
- 卸载命令不会执行 Docker Volume 删除或数据库操作。

### 4.5 自动化测试和 CI

要做什么：

- 建立可以阻止安全回归和部署回归的测试体系。

首批测试内容：

- WebHook Token、HMAC、分支过滤、项目匹配和非法请求。
- 登录限流、Cookie、Session 过期、CSRF 和密码重置。
- 配置解析、原子写入、备份、恢复和错误配置回退。
- 部署队列、取消、超时、失败、回滚和进程清理。
- 日志行数限制、下载上限、正则过滤和容器名校验。
- Nginx/systemd 配置生成及危险输入转义。
- 安装、升级、回滚和卸载脚本的 ShellCheck。

怎么做：

1. 新增 `tests/`，使用 `pytest`，通过临时目录隔离状态和配置。
2. 新增 `pyproject.toml`，集中配置 `pytest`、`ruff` 和开发依赖。
3. CI 测试 Python 3.10、3.11、3.12 和 3.13。
4. 使用 Ubuntu 容器运行安装脚本的非破坏性集成测试。
5. 每个安全修复必须先添加失败用例，再修改实现。

验收标准：

- Pull Request 必须通过 Python 测试、Ruff、ShellCheck 和 JavaScript 语法检查。
- 核心认证、WebHook 和配置逻辑覆盖率不低于 85%。
- CI 不需要真实服务器、真实仓库 Token 或公网域名。

## 5. P1：部署可靠性功能

### 5.1 WebHook 幂等与重复请求处理

实现方案：

- 优先读取 GitHub、Gitee、GitLab 的 Delivery ID。
- 没有 Delivery ID 时使用 `project + action + commit` 作为幂等键。
- 在状态文件中保存有限数量的幂等记录和过期时间。
- 已执行或已排队的相同任务返回原任务状态，不再次入队。

验收标准：代码平台重试相同请求时，只产生一次部署。

### 5.2 队列持久化和服务重启恢复

实现方案：

- 每次入队、出队和取消后原子写入队列快照。
- Agent 启动时恢复未开始的任务。
- 对重启时正在执行的任务标记为 `interrupted`，要求人工重试，不盲目续跑。
- UI 展示排队时间、任务来源和恢复状态。

验收标准：Agent 重启后，未执行任务不会静默丢失。

### 5.3 部署策略

计划增加：

- 同项目重复提交只保留最新一次的可选策略。
- 全局串行与“不同项目有限并发”两种模式。
- 每项目冷却时间、最大重试次数和手动审批开关。
- 维护窗口和禁止部署时间段。

实现时保持默认行为不变：默认仍为全局串行、失败不自动重试。

### 5.4 备份与灾难恢复

在 P0 最小安装恢复闭环之上，计划增加：

- 一键导出脱敏配置、版本信息和诊断报告。
- 加密导出包含 Secret 的完整备份。
- 恢复前校验配置版本和文件权限。
- UI 和 `v0.2.0` 本机运维 CLI 都能查看最近备份，但恢复操作只允许服务器终端执行。

## 6. P2：使用体验功能

### 6.1 首次接入向导

Docker 管理已增加停止容器删除（核对完整 ID、保留卷）和镜像列表、搜索、拉取、非强制删除。操作沿用登录、CSRF、维护锁和审计；本地模拟交互及自动化测试已验证，真实 Docker 删除/拉取待 Linux 实机验收。

入口方式引导已增加「保留项目自带入口 / 使用面板统一入口 / 转发到业务 Nginx」。仓库识别和项目体检会静态检查 Compose 的服务及端口声明，并提示当前容器/本机监听服务；不改写 Compose、不停止已有服务，也不作为部署阻断器。变量、覆盖规则和自定义脚本需人工确认。

Nginx 独立安装已支持本机和 Docker 两种方式，先运行 HTTP，无需业务项目、域名或证书。新增容器使用独立配置目录、只读挂载和可选 443 映射；已有容器不重建，未安装 Docker 时提示先准备运行环境。自动化测试覆盖参数、占用检查和失败清理，真实 Docker 安装及外部网络访问仍需 Linux 实机验收。

域名接入已增加检查/确认两步向导，支持缺少 Nginx 时通过系统包管理器安装本机版本，已有 Docker 接入保留高级配置。站点重载失败回退和冲突检查已有自动化测试；安装、systemd 和发行版包管理器仍需 Linux 实机验收。域名解析、云防火墙以及已有容器的挂载改造不自动执行。

2026-09-16：已接入仓库只读识别、模板选择、启动入口建议、部署文件预览和确认后初始化。默认保留已有脚本和服务文件；新安装空项目、添加首个项目、删除最后一个项目已补回归测试。识别目前覆盖根目录常见项目，不自动适配所有构建方式；Linux 完整部署实测和测试 WebHook 闭环仍待完成。

步骤规划：

1. 检查 Git、Docker、Nginx、磁盘和 SSH Key。
2. 选择项目类型和代码平台。
3. 验证仓库访问权限。
4. 生成部署脚本草稿并展示差异。
5. 运行部署前体检。
6. 生成平台对应的 WebHook 配置说明。
7. 发送一次测试 WebHook 并确认闭环。

向导必须允许跳过，已有用户仍可直接编辑高级配置。

计划增加：

### 6.3 部署详情和事件中心

2026-09-16：新增初始化和部署失败的规则诊断，覆盖仓库权限、分支、网络、依赖、端口、磁盘和超时等问题。建议随本次失败记录保存，不自动执行修复；旧历史记录不补猜测诊断。

- 部署日志与阶段时间线联动定位。
- 告警确认、静默、恢复和备注。
- 容器异常与对应部署记录关联。
- 审计日志搜索和脱敏导出。

### 6.4 通知策略

计划增加：

- 按项目、事件等级和状态选择通知渠道。
- 支持失败立即通知、恢复通知和重复告警合并。
- 增加通用 WebHook 通知渠道。
- 通知模板支持有限变量，不允许执行表达式或代码。

### 6.5 UI 质量

计划内容：

- 将通知、事件等视图改为静态 HTML 结构，减少运行时 DOM 重组。
- 完善键盘操作、焦点状态、ARIA 标签和颜色对比度。
- 覆盖桌面、平板和手机视口的截图回归测试。
- 大量日志、项目和容器场景使用分页或虚拟列表。
- 保持原生 JavaScript 和 CSS，不为普通页面引入大型前端框架。

## 7. P3：扩展与生态

### 7.1 代码平台适配器

将平台差异集中到适配器接口：

- 请求签名验证。
- 分支、提交、作者和变更文件解析。
- Delivery ID 和事件类型解析。
- 平台对应的配置说明。

首批正式支持 Gitee、GitHub 和 GitLab，其他平台通过社区适配器扩展。

### 7.2 项目模板包

模板应包含：

- 项目识别规则。
- 部署脚本模板。
- systemd 或 Docker Compose 建议。
- 健康检查默认值。
- 体检规则和常见错误提示。

计划提供 Python、Node.js、Go、Spring Boot、静态站点和 Docker Compose 模板。模板只生成草稿，不直接假设业务命令一定正确。

### 7.3 公开 API 和远程 CLI 模式

`v0.2.0` 已规划完成本机 `mini-deployctl` 的统一封装；本节不重复推迟本机备份、恢复或管理员命令，而是在其稳定后提供版本化的 `/api/v1` 和可选远程客户端模式：

- 允许 `mini-deployctl` 显式指定远程端点，并默认继续使用本机模式。
- 通过 API 查询状态、项目和日志，并触发具备明确权限范围的部署或取消操作。
- 服务器凭据、恢复、升级、版本回滚和卸载默认仍只允许本机终端执行，不直接暴露为远程高权限操作。
- 公开 API 使用独立版本号和兼容策略，不能直接复用内部 HTTP 路由。

API Token 必须独立于 WebHook Token，支持权限范围、过期时间和撤销。

### 7.4 可观测性

可选增加：

- Prometheus 文本格式指标端点，默认仅监听本机。
- 部署成功率、耗时、队列长度和失败阶段指标。
- 结构化 JSON 日志开关和 request ID。
- 诊断包导出时自动脱敏域名、Token、邮箱和路径。

## 8. 代码结构演进

在测试稳定后，将单文件 Agent 渐进拆分，避免一次性重写：

```text
mini_deploy/
  auth.py            # 登录、Session、CSRF、限流
  config.py          # 项目配置、备份、迁移
  deploy.py          # 队列、进程、取消、回滚
  webhooks.py        # 平台适配和签名校验
  system_status.py   # 系统及 Docker 状态
  notifications.py  # 通知渠道
  http_server.py     # 路由和响应
  models.py          # 数据结构
agent.py             # 兼容入口和启动流程
```

拆分规则：

- 每次只移动一个职责，并保持外部接口不变。
- 先补测试再移动代码。
- 不在重构提交中同时增加大型功能。
- `agent.py` 继续保留为安装脚本和 systemd 的稳定入口。

## 9. 明确不做的内容

为了保持项目轻量，近期不计划：

- 内置 Git 托管、代码评审或制品仓库。
- 替代 Kubernetes、Jenkins、GitLab CI 等大型平台。
- 自动执行数据库迁移、数据库回滚或 Docker Volume 删除。
- 在面板中提供任意 Shell 终端。
- 自动猜测所有项目的构建和启动方式。
- 为了展示效果引入必须长期运行的数据库、Redis 或消息队列。

## 10. Issue 拆分规范

每个路线图条目拆成 Issue 时应包含：

- 背景和用户问题。
- 明确的范围与非范围。
- 安全影响和兼容性影响。
- 配置或 API 变更。
- 实现步骤。
- 自动化测试清单。
- 文档更新清单。
- 可验证的验收标准。

建议标签：

- `priority/P0`、`priority/P1`、`priority/P2`。
- `area/security`、`area/deploy`、`area/ui`、`area/installer`、`area/docs`。
- `type/bug`、`type/feature`、`type/refactor`、`type/test`。
- `good first issue` 和 `help wanted`。

## 11. 每个版本的完成标准

发布前必须确认：

- 所有自动化测试和静态检查通过。
- 没有真实 Token、密码、域名或私有仓库信息进入 Git。
- 新增配置有默认值、示例和升级说明。
- 安装、升级和回滚在支持的 Linux 发行版上验证通过。
- UI 在桌面和移动端没有明显溢出、遮挡或不可操作控件。
- 安全相关日志完成脱敏。
- `CHANGELOG.md` 已更新。
- 发布包包含版本号、提交号和校验值。
- 可以按照文档从上一版本回滚。

## 12. 推荐执行顺序

首个公开测试版前先完成 WebHook 密钥保护、管理员初始化、权限拆分、最小升级/恢复/卸载闭环、私密漏洞与行为准则举报渠道配置和基础 CI。`v0.2.0` 再完成幂等队列、重启恢复、高级灾备和统一的本机运维 CLI；`v0.3.0` 处理 UI 向导与事件筛选；`v0.4.0` 扩展平台适配器、公开 API 和远程 CLI 模式。大型重构必须排在测试体系建立之后。

达到 `v0.1.0` 条件后先公开测试，通过真实服务器反馈修正两个小版本，再决定 `v1.0.0` 的最终兼容承诺。
